One POST, five layers

POST /api/v1/patients is the one complete workflow in the codebase. Step it through the layers with the buttons, or flip the scenario to see how a second registration of the same identifier takes the update branch instead. Every fact here comes from the code and the integration test that proves the behavior.

The request and the answer

  

    

      
Request body

      
{
  "identifierSystem": "http://hospital.example.org/mrn",
  "identifierValue": "MRN-1001",
  "familyName": "Doe",
  "givenName": "John",
  "birthDate": "1990-05-15",
  "gender": "male"
}

      
Validation on PatientRequest: identifierSystem,
      identifierValue, familyName, givenName and gender
      are @NotBlank; birthDate is @NotNull and
      @PastOrPresent. Failures become a 400 ProblemDetail before the service runs.

    

    

      
Response

      
HTTP/1.1 201 Created
Location: /api/v1/patients/pat-123
Content-Type: application/json

{
  "resourceId": "pat-123",
  "identifierSystem": "http://hospital.example.org/mrn",
  "identifierValue": "MRN-1001"
}

      
The body carries only three fields. Domain and FHIR types never cross the REST
      boundary; demographics are written to FHIR, not echoed back.

    

  






  
Sharp edges worth knowing

  
Two searches per POST
  PatientService.register searches by identifier, then FhirPatientAdapter.save
  searches again before deciding create or update. There is no transaction and no conditional create, so
  two concurrent first-time POSTs for the same identifier can both take the create branch.

  
The app database stays empty
  inbound_messages and resource_mappings exist as Flyway DDL, but no production
  code reads or writes them yet. The patient flow is entirely FHIR REST.

  
500s escape the documented error shape
  A down FHIR server, more than one identifier match, or a create that returns no id all throw
  IllegalStateException and surface as Spring Boot's default 500 JSON, not the RFC 7807
  ProblemDetail used for 400 and 404.

  
gender is only checked for blankness
  A non-blank but invalid code passes HTTP validation, then fails in
  FhirPatientMapper with IllegalArgumentException → 500.






  
Reading one patient back

  

    

      
GET /api/v1/patients/{id} takes a FHIR resource id, never the MRN. The controller
      calls PatientService.findById, the adapter does a FHIR read
      (GET /fhir/Patient/{id}), and a missing resource becomes a 404 ProblemDetail:
      title: "Not Found", detail: "No patient found with resource id pat-404".

    

    

      
client.read().resource(Patient.class)
    .withId(resourceId)
    .execute();
