Explainer 3 · Architecture

Five modules, one direction

The platform is a modular monolith: one Spring Boot deployable built from five Maven modules, with the dependency direction enforced by tests instead of good intentions. Click a box in the graph to see what lives inside the module and which boundaries apply to it.

Solid arrows are compile dependencies; the dashed arrow is the test module compiling against the application. No cycles allowed, and the bottom module depends on nothing else.

The two boundary tests

DomainArchitectureTest unit

Runs under Surefire in healthcare-domain. Four ArchUnit rules, all with allowEmptyShould(true):

  • domain classes depend only on java.. and themselves
  • no org.springframework.. imports
  • no jakarta.. imports
  • no ca.uhn.. (HAPI) imports

The first rule already implies the other three; the explicit bans produce clearer failure messages.

ModuleDependencyIT integration

Runs under Failsafe in healthcare-integration-tests, over production bytecode of all modules. Four rules:

  • domain depends on no other module
  • hl7 does not depend on fhir or application
  • fhir does not depend on hl7 or application
  • slices com.example.healthcare.(*).. are free of cycles

Only healthcare-application may point at the other three, which is exactly what its POM does.

Build and test commands

./mvnw test            # unit tests only, no Docker
./mvnw verify          # all tests, adds *IT classes
./mvnw verify -Dit.test=PatientWorkflowIT
./mvnw -pl healthcare-domain test
./mvnw -pl healthcare-integration-tests -am \
    verify -Dit.test=ModuleDependencyIT

Surefire runs *Test and excludes *IT. Failsafe runs only *IT during verify, with failIfNoSpecifiedTests=false so a targeted -Dit.test= run does not fail modules that lack that class.

exec classifier The application module builds an executable jar with the exec classifier, so the plain jar stays the main artifact and the integration test module can compile against application classes.
