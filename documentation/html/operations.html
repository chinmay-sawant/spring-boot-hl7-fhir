Explainer 5 · Running locally

The local stack, started in one script

Three containers, one Maven command. The application itself is not a container in the dev loop; it runs on the host and talks to the HAPI FHIR server on port 8080. Press the button to replay what ./scripts/start-local.sh prints.

What Compose brings up

app-postgres localhost:5432 → 5432

postgres:17.11. Application database, named volume app-postgres-data, healthcheck pg_isready. The only database published to the host.

fhir-postgres no host port

postgres:17.11. FHIR storage, named volume fhir-postgres-data, reachable only by hapi-fhir on the Compose network. Same healthcheck pattern.

hapi-fhir localhost:8080 → 8080

hapiproject/hapi:v8.12.0-2-tomcat. Waits for fhir-postgres to be healthy, then starts; healthcheck is curl /fhir/metadata with a 180s start period.

Why the tomcat image The default hapiproject/hapi image is distroless and ships no shell or curl, so the /fhir/metadata healthcheck could not run. The -tomcat variant carries curl.

Configuration and environment

Profiles

default (application.yml): port 8081, only /actuator/health exposed with details hidden, ECS structured console logs, FHIR base URL http://localhost:8080/fhir.

dev: imports ./.env and ../.env (both optional), binds the datasource from APP_DB_*, FHIR base URL from HAPI_FHIR_PORT.

test: inert datasource on port 65535, Flyway disabled. Used by the context and unit tests; the integration test overrides datasource and FHIR URL dynamically instead.

Timeout and TZ notes

HAPI can take a while on first start: healthcheck budget is 180s start period plus 18 retries of 10s. Override the script budget with START_LOCAL_TIMEOUT=900 ./scripts/start-local.sh.

Both integration tests pin TimeZone.setDefault(UTC) because the PostgreSQL driver forwards the host zone and postgres:17.11 rejects legacy aliases such as Asia/Calcutta. If your host still uses one, run tests as TZ=UTC ./scripts/run-tests.sh.
