Explainer 4 · Data ownership

Two databases, one identity

Clinical resources live in the HAPI FHIR server's PostgreSQL database. Operational metadata (message state, resource mappings) lives in the application's own PostgreSQL database. One writer each, no distributed transactions, and an identity model that survives retransmissions. Explore the tables below; the schema is verified by DatabaseMigrationIT against a real postgres:17.11 container.

Who owns what

Application PostgreSQL owned by us

Message control ids, processing status, retries, resource mappings, and (planned) audit records. Operational metadata only; never a full clinical record. Migrated with Flyway from healthcare-application/src/main/resources/db/migration.

Published on localhost:5432 in the dev stack.

FHIR PostgreSQL owned by HAPI

Patient, Encounter, Observation, Condition, DiagnosticReport, and every other clinical resource. HAPI is the only writer; the Spring app never opens a connection to this database, and it has no host port in the Compose stack. The schema belongs to the pinned server image.

Reachable only from the hapi-fhir container on the Compose network.

No distributed transaction A FHIR transaction Bundle is atomic inside FHIR, not with the application database. Consistency comes from idempotent replay: the unique key on inbound_messages, the identifier search before create, and the resource_mappings table. This is ADR-0004 and ADR-0005 in practice.

Identity: external key versus resource id

Business identifier

The pair that comes from the outside world: an assigning authority (system) and a value, for example http://hospital.example.org/mrn + MRN-1001. For HL7 it is PID-3 (authority from component 4, value from component 1). This is the matching key.

FHIR resource id

Assigned by the FHIR server on create and never derived from the identifier. The app extracts it from MethodOutcome.getId().getIdPart(). The REST API uses it in paths: GET /api/v1/patients/{id}.

resource_mappings

Links the two worlds per source: source system + source identifier + resource type to a FHIR resource id. A retransmitted message resolves to the same resource instead of creating a second one. Written by the planned HL7 handlers; not used by the REST flow today.

Never assume equality identifierValue is never assumed to equal the FHIR resource id. Every lookup goes through a FHIR identifier search: Patient?identifier=<system>|<value>.

Table explorer

Processing status values

The processing_status column is a VARCHAR(30) with the full state machine already named in V1:

RECEIVED VALIDATED PROCESSING COMPLETED RETRY_PENDING QUARANTINED

Plan 02 uses the first four (plus error recording); plan 04 adds the retry and quarantine transitions.

Doc drift, verified documentation/architecture/database-design.md lists created_at and updated_at as nullable. The actual migration declares both TIMESTAMPTZ NOT NULL DEFAULT now(), and DatabaseMigrationIT asserts they are NO nullable. The table explorer shows the code truth.
