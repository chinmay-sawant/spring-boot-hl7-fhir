FHIR: a beginner's reference

FHIR (Fast Healthcare Interoperability Resources) is how modern health systems exchange clinical data over ordinary web APIs: small JSON documents called resources, linked by references, coded with standard vocabularies. This page explains the whole idea using only this demo's data and endpoints, so everything here is verifiable on your own machine.

1. Overview: what FHIR is and why it exists

Before FHIR, hospitals mostly exchanged HL7 version 2 pipe-delimited messages and CDA clinical documents. Both work, but v2 fields are positional (PID-5 is a name only because everyone agreed it is), and CDA documents are large XML files that are hard to query field by field. Every new integration meant custom parsing and bilateral agreements about what each position meant.

FHIR keeps the hard-won clinical semantics and rebuilds the plumbing on web standards: REST for transport (read a record with GET, search with query strings), JSON for shape (named fields instead of positions), and standard vocabularies for meaning (a lab test is a LOINC code, not a local string). The result reads like any other web API: GET /api/patients/patient-1 returns a Patient, GET /api/observations?patient=patient-1 returns that patient's labs.

The 80/20 ruleFHIR was designed around the 80/20 rule: standardize the 20% of fields that cover 80% of use cases (patient name, birth date, lab code, value), and leave the rest to optional fields and extensions. That is why a Patient can be just a name plus a birth date, while still having room for telecom, address, and identifiers when you need them.

2. What is a resource?

A resource is one small, self-describing JSON document about one thing: one patient, one lab result, one visit, one clinician. Every resource has the same skeleton:

FieldMeaningExample from this demo
resourceTypeWhich kind of resource this is. Always present."resourceType": "Patient"
idLogical id, unique within this server. Used in references."id": "patient-1"
metaVersioning and profile tags added by the server. Optional in our sample files.Omitted in bundled samples; servers add it on write.
narrative (text.div)Human-readable XHTML summary, a best-practice fallback for display.Omitted in bundled samples - this is exactly what the dom-6 validator warning flags (see section 6).

Everything else on a resource is domain fields: Patient.name, Observation.valueQuantity, Encounter.period. Unknown fields are not silently accepted - the resource type defines what is legal, and validation enforces it.

R4 vs other releasesFHIR grew through DSTU2 (early draft), STU3 (trial use), and then R4 (Release 4, 2019), the first normative release whose core resources are stable and backward-compatible going forward. R4B (2022) added only balloted extras, and R5 (2023) is the newest normative edition. R4 is the widely-adopted core used here - this demo runs HAPI FHIR 7.4.0 in R4 mode, and every sample file is an R4 resource.

3. Tour of the four resources in this demo

Each card below names the required vs optional fields that matter here, with snippets copied verbatim from the bundled sample files in src/main/resources/fhir-samples/.

Patient: who the person is

Required in practice: resourceType plus enough identity to be useful (usually a name or identifier). gender, birthDate, telecom, address, and active are all optional in the base spec but carry the demographics every downstream system needs.

{
  "resourceType": "Patient",
  "id": "patient-1",
  "identifier": [
    {
      "system": "http://hospital.example.org/mrn",
      "value": "PATIENT-1"
    }
  ],
  "active": true,
  "name": [
    {
      "use": "official",
      "family": "Smith",
      "given": ["John", "A"]
    }
  ],
  "telecom": [
    {
      "system": "phone",
      "value": "(217) 555-0100",
      "use": "home"
    }
  ],
  "gender": "male",
  "birthDate": "1980-05-15",
  "address": [
    {
      "use": "home",
      "line": ["123 Main St"],
      "city": "Springfield",
      "state": "IL",
      "postalCode": "62701",
      "country": "USA"
    }
  ]
}

File: patient-1.json - Smith/John, male, 1980-05-15. Confirm live with GET /api/patients/patient-1.

4. References and linking

Resources point at each other with references of the form ResourceType/id. The lab does not embed the patient; it points at the patient:

"subject": {
  "reference": "Patient/patient-1",
  "display": "John A Smith"
}

In this demo, Observation.subject.reference is Patient/patient-1, Encounter.subject.reference is Patient/patient-1, and Encounter.participant[0].individual.reference is Practitioner/practitioner-1. The display string is a convenience label only - the reference is what the server follows.

Vs HL7v2 implicit bundlingAn HL7v2 ADT message bundles one visit implicitly: PID (patient) and PV1 (visit) sit in the same message, so linkage is by position, not by pointer. FHIR inverts this: each resource stands alone and links explicitly. That is why one Observation can be fetched, validated, and updated without re-sending the whole chart - and why GET /api/observations?patient=patient-1 is a search over links, not a scan of bundled messages.

5. REST API: read, search, create, update

FHIR servers expose each resource type as a URL path. This demo mirrors the standard shape under /api:

OperationFHIR shapeIn this demo
Read oneGET /Patient/{id}GET /api/patients/patient-1 - full Patient JSON
SearchGET /Patient?name=SmithGET /api/patients?name=Smith - match on family/given
Search by linkGET /Observation?patient=Patient/patient-1GET /api/observations?patient=patient-1 - labs for one patient
CreatePOST /Patient with a resource bodySame pattern; the server assigns or honors the id
UpdatePUT /Patient/{id} with the full replacement bodySame pattern; full resource, not a patch

Search parameters are per-resource query keys defined by the spec (name, birthdate, gender on Patient; patient, code, status on Observation). Servers may support more or fewer; this demo supports the subset its endpoints document. A multi-result search on a full FHIR server returns a Bundle of type searchset - one JSON document wrapping all matches plus paging links - whereas this demo returns the match list directly to keep the learning curve flat.

6. Profiles, extensions, validation

A profile tightens the base resource for a use case: it says which optional fields become required, which value sets are allowed, and what cardinality each field has. Cardinality 1..1 means exactly one occurrence is required - Observation.status is 1..1, which is why deleting it makes validation fail. Must-support is softer: it flags fields clients must be able to handle (like Observation.valueQuantity), without making them strictly required.

The 80/20 rule needs an escape hatch, and that hatch is extensions: namespaced extra fields (url + value) for data the core spec did not standardize. Extensions keep everyone interoperable on the core while letting regions and vendors carry local needs without forking the spec.

What the demo validator checksTry GET /api/demo/validate?resource=... (walkthrough step 7): the HAPI validator runs the resource against its R4 profile offline. The classic result is the dom-6 warning - a resource should have a narrative (text.div) as a best-practice fallback for human display. Our bundled samples omit the narrative on purpose, so even a valid Patient earns that warning. It is a warning, not an error: machine-readable data is complete; only the human-readable backup is missing.

7. Terminology: LOINC, SNOMED CT, UCUM

Codes are what make FHIR data comparable across hospitals. Three systems do most of the work in this demo:

SystemRoleDemo example
LOINCNames lab tests and measurements universally.Observation.code = 718-7, Hemoglobin [Mass/volume] in Blood, with human text "Hemoglobin" alongside.
SNOMED CTNames clinical concepts: conditions, procedures, service types.Encounter.serviceType = 394575009, Outpatient (system http://snomed.info/sct).
UCUMUnits of measure, so 14.2 is unambiguous.Observation.valueQuantity = 14.2 g/dL (system http://unitsofmeasure.org, code g/dL).

The pattern is always the same Coding shape - system (which dictionary), code (the entry), display (human label) - plus an optional plain text fallback. Compare the demo's LOINC block with the HL7v2 equivalent: in v2 the test name rides as free text in OBX-3; in FHIR the machine-readable code is primary and the text is the backup.

8. Summary and where to go next

FHIR is REST plus JSON plus coded meaning: small typed resources, explicit references instead of bundled segments, standard vocabularies instead of local strings, and profiles plus validation to keep everyone honest. R4 is the stable core this demo teaches.
