Theory · how v2 and FHIR coexist

HL7v2 and FHIR, together

Hospitals do not get to pick one messaging standard and start over. Decades of HL7v2 feeds run the wards, labs, and billing systems today, while new apps and portals speak FHIR. This page explains how the two live side by side - and how this demo's ADT^A01-to-Patient conversion fits into that picture.

1. Overview: why hospitals run both

HL7v2 has carried admission, discharge, lab, and order messages between hospital systems since the late 1980s. Every admission desk, lab analyser, and billing interface in a typical hospital already speaks some dialect of v2, and replacing all of it at once is neither affordable nor safe. Meanwhile, patient portals, mobile health apps, and cross-organisation sharing need modern REST APIs with precisely coded data - which is what FHIR R4 provides.

The result is coexistence, not replacement. New FHIR APIs are layered on top of, and alongside, existing v2 feeds: an admission still arrives as an ADT message from the hospital information system, and a FHIR facade or interface engine exposes the same facts as Patient and Encounter resources for newer consumers. Expect this dual world to last at least the next decade, so working clinicians' software engineers need to read both formats and convert between them with care.

NoteThis demo shows the coexistence pattern in miniature: one ADT^A01 message converts on demand to a FHIR R4 Patient via GET /api/hl7v2/to-fhir, returning {"resourceType":"Patient","family":"Smith","given":["John"],"gender":"male","birthDate":"1980-05-15"}.

2. One event, two expressions: patient admission

When John Smith is admitted, the hospital information system fires an ADT^A01 (admit/visit notification) message. In HL7v2 the whole event is one flat message of segments; in FHIR the same facts become two linked resources - a Patient (who the person is) and an Encounter (this particular visit).

HL7v2: ADT^A01 segments

Positional, pipe-delimited. One message carries header, identity, and visit together:

MSH|^~\&|HIS|HOSP|EHR|HOSP|202401151030||ADT^A01|MSG-1|P|2.5
EVN||202401151030
PID|1||PATIENT-1^^^HOSP^MR||Smith^John||19800515|M
PV1|1|O|||||||||||||||VISIT-1

MSH routes the message, PID identifies the patient, PV1 describes the visit.

FHIR R4: Patient + Encounter

Named JSON fields with explicit links. Identity and visit are separate resources:

{
  "resourceType": "Patient",
  "family": "Smith",
  "given": ["John"],
  "gender": "male",
  "birthDate": "1980-05-15"
}
{
  "resourceType": "Encounter",
  "class": { "code": "AMB" },
  "subject": { "reference": "Patient/patient-1" }
}

The Encounter points at the Patient with subject.reference instead of bundling everything in one message.

MSH: the envelope, not the content

MSH (message header) fields - sending application, facility, timestamp, message control ID - describe the message itself: who sent it, when, and which message it is. They do not convert into Patient or Encounter clinical fields. In a full FHIR messaging exchange they would map onto a Bundle of type message plus a MessageHeader resource carrying the sender, timestamp, and event code; in this demo the MSH fields are parsed and visible via GET /api/hl7v2/parse but only the clinical PID fields are converted by GET /api/hl7v2/to-fhir.

4. What gets lost or needs judgment

WarningConversion between v2 and FHIR is never purely mechanical. The rows below need a human decision or a documented local rule - silent defaults here cause real patient-safety and billing errors.
ProblemWhy it needs judgment
Name use codesFHIR names carry a use (official, maiden, nickname). PID-5 type codes do not line up one-to-one, so the converter must choose a default (usually official) and document it.
Visit class O vs Encounter.classHL7v2 patient classes (O outpatient, I inpatient, E emergency) overlap FHIR encounter-class codes (AMB, IMP, EMER) but the value sets differ. Each local code needs an explicit mapping row, not a guess.
Identifiers without systemsA bare PATIENT-1 with no assigning authority has no safe FHIR system URI. This demo hard-codes http://hospital.example.org/mrn; a real interface must derive the system from the sending facility or reject the message.
Narrative textFree-text notes and comments in v2 (NTE segments) have no single FHIR home - they may belong in Annotation, narrative, or a DocumentReference. Dropping them silently loses clinical context.

5. Interface engines: the plumbing between v2 and FHIR

Hospitals rarely convert messages by hand in each application. Instead, an interface engine sits in the middle: it receives messages from senders, routes them to the right receivers, transforms formats, and queues messages so nothing is lost when a receiver is down.

Mirth Connect (NextGen Connect). The widely used open-source interface engine. It solves the routing and transformation problem with message channels: a channel listens on one endpoint (for example MLLP for v2), runs a transformer script that maps PID and PV1 fields to FHIR JSON, and forwards the result to a FHIR endpoint - queuing messages durably if the destination is offline.

Rhapsody. A commercial integration engine used by large health networks. It solves the same routing, transforming, and queuing problem but adds managed FHIR API tooling, prebuilt clinical mappings, and operational monitoring aimed at high-volume, multi-facility traffic where guaranteed delivery and audit trails are contractual requirements.

Demo connectionThis demo's Hl7v2Service plays the transformer role of a one-channel interface engine: parse on one side, FHIR JSON on the other - without the queues, routing tables, or monitoring a production engine provides.

6. Migration strategies

Greenfield FHIR. Build new systems and new exchanges natively on FHIR and leave legacy v2 feeds untouched. Works for new departments, apps, or organisations with no legacy estate; fails wherever the old feeds remain the system of record.

Facade / proxy over v2. Keep the v2 feeds and the existing database as the source of truth, and put a FHIR API in front that converts on demand. Cheapest path to FHIR compatibility and the lowest migration risk - but quirks and data gaps in the v2 feed leak straight through the FHIR API.

Incremental domain-by-domain. Migrate one clinical domain at a time - patients and scheduling first, then labs, then medications - running v2 and FHIR in parallel per domain until each cuts over. The most realistic enterprise path, but it requires maintaining two integrations and careful reconciliation during each overlap period.

NoteThis demo resembles the facade strategy: Hl7v2Service converts the ADT message to FHIR on demand, while the H2 database stays the source of truth. Nothing is migrated; the FHIR view is derived whenever GET /api/hl7v2/to-fhir is called.

7. Hands-on: parse, convert, round-trip

Run these three tasks in order against the running demo (default port 8080). Each builds on the previous one: first see the parsed segments, then the FHIR conversion, then feed new demographics back through the generator.

  1. Parse. Inspect the raw ADT^A01 segments field by field: 
    curl http://localhost:8080/api/hl7v2/parse
  2. Convert to FHIR. Confirm the PID mapping - Smith, John, male, 1980-05-15: 
    curl http://localhost:8080/api/hl7v2/to-fhir
  3. Generate round-trip. Build a fresh ADT message from demographics, then re-parse it to verify the fields survived: 
    curl -X POST "http://localhost:8080/api/hl7v2/generate?family=Test&given=User&dob=20000101&gender=M&id=999"

8. Summary

Hospitals will run HL7v2 and FHIR together for years: v2 carries the operational feeds, FHIR serves the APIs. One admission is either a flat ADT^A01 message or a linked Patient plus Encounter; the PID and PV1 rows above show exactly how each field crosses over, with MSH becoming message-envelope metadata. Conversion always involves judgment - name use, class codes, identifier systems, and narrative text need explicit rules. Interface engines do the routing, transforming, and queuing at scale, migration usually proceeds behind a facade or domain by domain, and this demo is a small facade you can drive with three curl commands.
