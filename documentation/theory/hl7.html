Theory · HL7

HL7, from zero to the demo message

This page is the beginner's reference for everything before FHIR: what HL7 the organization publishes, how the pipe-delimited v2 format works, and what each line of the demo's adt-a01.hl7 file means. Read it top to bottom once, then use it as a lookup.

1. Overview: HL7 the organization and the standards family

HL7 (Health Level Seven) is a standards organization for health-care data exchange; the "seven" refers to the seventh layer of the OSI networking model, the application layer. It publishes a family of standards that solve the same problem - moving clinical and administrative data between systems - with different technology for different eras. This demo touches two of them: HL7v2 (the pipe-delimited messages you will parse below) and FHIR (the REST + JSON resources on the other side).

HL7v2

The workhorse since the late 1980s: flat, pipe-delimited messages such as ADT^A01 sent over TCP (often with MLLP framing) through interface engines. Positional fields (PID-5 = patient name), cheap to produce and parse, still carrying most admit/discharge, lab, and radiology feeds in hospitals today. This page covers it in full.

HL7v3

The 2000s successor attempt: XML messages built on a single object model (the Reference Information Model). Precise but heavy - every message carried the full weight of the model, tooling was complex, and adoption stayed limited compared to v2.

CDA (Clinical Document Architecture)

A v3-derived standard for clinical documents (discharge summaries, lab reports) rather than event messages: an XML document with a human-readable narrative plus optional machine-readable entries. Widely used for document exchange where v2 messages were too granular.

FHIR

The current standard: REST + JSON resources (Patient, Observation, Encounter) with coded meaning and explicit links between records (Observation.subject points at Patient/patient-1). Field names carry the meaning instead of field positions. See Theory: FHIR and the comparison in FHIR vs HL7v2.

2. What is HL7v2?

HL7 version 2 is a messaging standard for real-time, event-driven exchange between hospital systems: when something happens (a patient is admitted, a lab result is ready), the source system fires a text message at whoever subscribed to that event. The format dates to the late 1980s, when bandwidth was scarce and parsers were simple: each message is a handful of plain-text lines with fields separated by pipes (|) and sub-parts separated by carets (^). No JSON, no schemas on the wire - both sides just agree on positions: the fifth field of the PID segment is always the patient name. That made v2 trivial to implement on the hardware of the day and easy to route through interface engines, which is why it won.

It still runs today wherever the original plumbing was laid and never needed replacing: ADT (admit/discharge/transfer) feeds that keep the census and billing systems in sync, lab (ORM/ORU) orders and results, radiology orders, pharmacy, and device interfaces. New development tends to choose FHIR, but any working hospital still speaks v2 on the inside - which is why this demo starts there.

3. Message anatomy

Segments, fields, components, sub-components, repetitions

A v2 message is a sequence of segments, one per line, each starting with a three-letter code (MSH, EVN, PID, PV1). Segments are split into fields by | and addressed by position: PID-5 means "PID segment, fifth field". A field can be split into components by ^ (Smith^John = family + given name), components into sub-components by &, and a whole field can repeat, with repeats separated by ~ (for example two phone numbers in one field). Empty fields are simply left blank between pipes (||), which is why raw v2 is full of consecutive pipes.

Delimiters

NoteThe sender can theoretically choose different delimiters, but in practice every feed uses | ^ ~ \ &, and the demo file does too. The MSH-2 value ^~\& is how a parser knows for sure.

EVN - the event wrapper

EVN carries the event metadata: what happened and when it was recorded. In the demo it is minimal - EVN||20240115120000: EVN-1 (event type code) is empty and EVN-2 (recorded date/time) repeats the message timestamp. Real feeds usually put the trigger code (e.g. A01) in EVN-1, but the authoritative trigger lives in MSH-9 anyway.

PID - patient identity

PID identifies the person. Four fields do most of the work in this demo:

FieldNameDemo valueBreakdown
PID-3Patient identifier listPATIENT-1^^^HOSPITAL^MRCX type: id PATIENT-1, assigning authority HOSPITAL, identifier type MR (medical record number). This is the value that becomes the FHIR identifier.
PID-5Patient nameSmith^John^A^^^^LXPN type: family Smith, given John, middle A, name-type L (legal). Becomes FHIR name: [{family: "Smith", given: ["John"]}].
PID-7Date/time of birth19800515DTM type, date-only precision: 15 May 1980. Becomes FHIR birthDate: "1980-05-15".
PID-8Administrative sexMIS type: M = male. Becomes FHIR gender: "male".

The same segment also carries supporting demographics you can spot by position: PID-1 set ID (1), PID-11 address (123 Main St^^Springfield^IL^62701^USA), PID-13 phone ((217)555-0100), PID-16 marital status (S = single), and PID-18 account number (PATIENT-1).

PV1 - the visit

PV1 describes the encounter (the visit), not the person - this is the segment-level version of the split FHIR makes between Patient and Encounter. In the demo: PV1-1 set ID (1), PV1-2 patient class (O = outpatient - belongs on Encounter.class, not on Patient), PV1-3 assigned location (OPD^^^HOSPITAL: point of care OPD, facility HOSPITAL), PV1-7 attending doctor (12345^House^Gregory: id, family, given), PV1-19 visit number (V12345), and PV1-44 admit date/time (20240115120000). Everything between is empty - one message carrying one visit, with the linking left implicit.

4. Data types

Fields are typed, but the type lives in the specification, not in the message - the parser knows PID-5 is a name only because the standard says so. The four types that matter for this demo:

5. Trigger events and message types

MSH-9 answers "what kind of message is this, and what event fired it?" in three components: message code, trigger event, message structure. The demo's ADT^A01^ADT_A01 reads as: message family ADT (Admit/Discharge/Transfer - patient administration), trigger A01 (admit / visit notification - "this patient arrived"), following the ADT_A01 segment layout. The trigger is the meaningful part: it tells the receiver which business event just happened so it knows what to do with the demographics attached.

TriggerNameWhen it fires
ADT^A01Admit / visit notificationPatient arrives (this demo's message).
ADT^A02Transfer a patientPatient moves location (bed, unit, facility); PV1-3 carries the new assignment.
ADT^A03Discharge / end visitVisit ends; the visit opened by the A01 is closed out.
ADT^A08Update patient informationDemographics changed without an admit/transfer/discharge (name correction, new phone number).

The pattern generalizes: other families pair their own triggers the same way (e.g. ORM orders, ORU results), but ADT is the one this demo exercises.

6. ACK and reliability

Every v2 message expects an ACK (acknowledgment) message back, matched by MSH-10 control ID, with an MSA segment carrying accept (AA), error (AE), or reject (AR) codes. In original mode, a single ACK covers both transport receipt and application processing, so the sender only learns "it worked" after the receiver has fully handled the message. In enhanced mode, the two are split: an immediate accept acknowledgment confirms safe receipt (so the sender can move on), and a later application acknowledgment reports the processing outcome - at the cost of the sender having to correlate two responses per message instead of one.

7. Strengths and limits of v2

v2's strengths are why it is still running feeds decades later: plain text over a socket is trivial to emit, parse, and route through interface engines, and the event-driven model (fire an A01 when someone arrives) fits hospital workflows exactly. Its limits are the mirror image, and they are why FHIR came later: positional fields are fragile (one stray pipe shifts everything, and meaning lives in positions, not names); linking is implicit (one message bundles one visit, with no equivalent of a reference like Patient/patient-1); and coded meaning is thin (a bare M or O instead of a typed field). FHIR answers each of these with REST + JSON resources, explicitly linked records, and named fields with coded values - the web-API model replacing the always-the-same-layout fax. The side-by-side table in FHIR vs HL7v2 shows exactly how the demo's message maps across that gap.

8. Annotated walkthrough of the demo's adt-a01.hl7

The file is src/main/resources/hl7-samples/adt-a01.hl7: four segments (MSH, EVN, PID, PV1) separated by carriage returns, describing the admission of John Smith (DOB 15 May 1980, male) as outpatient visit V12345. Each segment below ties back to the theory above.

MSH - who sent what, and which event

MSH|^~\&|SENDING_APP|SENDING_FAC|RECEIVING_APP|RECEIVING_FAC|20240115120000||ADT^A01^ADT_A01|MSG00001|P|2.5.1

Encoding characters declared up front (MSH-2), demo sender/receiver placeholders (MSH-3–MSH-6), timestamp (MSH-7), empty security field (the || at MSH-8), message type ADT^A01^ADT_A01 (MSH-9, section 5), control ID MSG00001 for ACK matching (MSH-10, section 6), production flag (MSH-11), version 2.5.1 (MSH-12).

EVN - when it was recorded

EVN||20240115120000

Empty event-type code (EVN-1; the real trigger already lives in MSH-9) plus the recorded date/time in EVN-2, matching the message timestamp.

PID - who the patient is

PID|1||PATIENT-1^^^HOSPITAL^MR||Smith^John^A^^^^L||19800515|M|||123 Main St^^Springfield^IL^62701^USA||(217)555-0100|||S||PATIENT-1

Set ID 1 (PID-1); identifier PATIENT-1 issued by HOSPITAL as type MR (PID-3, CX); legal name Smith, John, middle A (PID-5, XPN); birth date 15 May 1980 (PID-7, DTM); sex male (PID-8, IS); street/city/state/ZIP/country address (PID-11); phone (PID-13); marital status single (PID-16); account number (PID-18). The PID-3/PID-5/PID-7/PID-8 rows are exactly the mapping table in FHIR vs HL7v2.

PV1 - which visit this is

PV1|1|O|OPD^^^HOSPITAL||||12345^House^Gregory||||||||||||V12345|||||||||||||||||||||||||20240115120000

Set ID 1 (PV1-1); patient class outpatient (PV1-2 - an Encounter property in FHIR, not a Patient one); assigned location OPD at HOSPITAL (PV1-3); attending doctor Gregory House, id 12345 (PV1-7); visit number V12345 (PV1-19); admit date/time (PV1-44). The long runs of pipes are the empty fields between them.

NoteOpen the raw file in an editor with visible control characters: segments end with a carriage return (\r), the v2 segment terminator - that is why the file can look like one long line where line endings are not rendered.
