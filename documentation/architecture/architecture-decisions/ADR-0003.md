# ADR-0003: HAPI FHIR server as the source of truth for clinical resources

## Status

Accepted, 2026-10-08.

## Context

The platform handles Patient, Encounter, Observation, DiagnosticReport, ServiceRequest, AllergyIntolerance, Condition, and MedicationRequest resources (init.md master prompt section 6). It needs storage, validation, search, references, conditional operations, transaction Bundles, and history for all of them.

A HAPI FHIR R4 JPA server provides those capabilities and is already part of the local stack. Keeping a parallel clinical schema in the application database would create two copies of the clinical record that drift apart, and every workflow would need reconciliation logic. init.md section 1 states the rule directly: the FHIR server is the source of truth, and the Spring Boot application should not maintain a duplicate clinical database.

## Decision

All clinical resources live in the HAPI FHIR server. The application reads and writes them only through the FHIR REST API with the HAPI FHIR client. Resource ids and history belong to the server.

The application database stores operational metadata only: message control ids, processing status, resource mappings, and audit records. The Flyway migrations contain no clinical resource tables, which plan 01 phase 5 verifies by creating only `inbound_messages` and `resource_mappings`. The FHIR database is owned by the server, sits behind it, and is never queried directly.

## Consequences

- One place holds clinical truth. There is no sync job between two clinical stores, and no conflict resolution for clinical fields.
- FHIR validation and search semantics come from the server, so the platform learns the real behavior of FHIR R4 instead of a hand-rolled approximation.
- The FHIR server becomes a runtime dependency of every clinical workflow. Its availability affects admissions and registrations, which is why retries, backoff, and the processing state machine exist ([ADR-0005](ADR-0005.md)).
- Queries that SQL would make trivial must go through FHIR search. The practical answer is to store the identifier mapping in `resource_mappings` and search by business identifier when the resource id is unknown.
- The FHIR database schema belongs to the pinned server version. Application migrations never touch it ([ADR-0004](ADR-0004.md)).
- Verification: plan 01 phase 5 creates no clinical tables, and phase 6 proves that re-registering the same identifier leaves exactly one FHIR Patient.

## Alternatives

- Mirror clinical resources into the application database for fast queries. Rejected because duplicate clinical storage drifts, doubles the write paths, and is explicitly discouraged in init.md section 1.
- Skip the FHIR server and persist clinical data in the application only. Rejected because the project would lose FHIR validation, search, transactions, and the interoperability experience that is the point of the platform.
- Use a hosted FHIR service instead of a local server. Rejected because the learning goal includes running the stack locally and because the brief defines a separate local HAPI FHIR server.

Source: init.md section 1, master prompt sections 6 and 8.
