# ADR-0002: Simplified hexagonal layering

## Status

Accepted, 2026-10-08.

## Context

The same business workflows must serve two input styles. A patient admission arrives as an HL7 v2 message from the hospital, and a similar admission can arrive as a REST call. The repository layout in init.md section 2 and the hexagonal sketch in init.md section 3 both separate business logic from interoperability technology so the workflows are written once.

Without a layering rule, admission logic drifts into an HL7 parser, FHIR mapping decisions drift into mappers, and the workflows become impossible to test without a FHIR server.

## Decision

The application follows the simplified hexagonal layout from init.md section 3:

- Input adapters accept REST calls and HL7 messages and translate them into calls on the application layer.
- The application layer holds the use cases for patient, encounter, laboratory, and clinical workflows.
- The domain holds entities, identifiers, and business rules. Domain rules stay independent of transport formats: a rule such as "the same identifier never creates a second patient" lives in the use case or the domain, never in a parser or a mapper.
- Ports are interfaces the domain needs from outside, starting with `PatientRepositoryPort.findByIdentifier` and `save`.
- Outbound adapters implement the ports. The FHIR adapter uses the HAPI FHIR client; the database adapter owns operational state.
- Mappers translate between representations and hold no business decisions. A mapper may decide how PID-5 becomes a HumanName; it may not decide whether a patient is admitted.

Plan 01 phase 2 enforces the direction: the domain purity test keeps Spring, jakarta, and ca.uhn out of `healthcare-domain`, and the module dependency test keeps `healthcare-hl7` and `healthcare-fhir` independent of each other.

## Consequences

- Use cases are testable with a mocked port, which is how plan 01 phase 6 tests patient registration without a FHIR server.
- HL7 input and REST input share one implementation of each workflow, per init.md section 2.
- FHIR R4 models are allowed at the boundary, so mapping code is explicit and confined to `healthcare-fhir`.
- The design has more interfaces than a plain layered architecture, and there is a standing risk of over-abstraction. init.md directs straightforward code and no unnecessary generic abstractions, so ports are added when a real second implementation or a test seam exists.
- Reviewers must watch for decisions creeping into mappers. The rule is named in this record so it can be pointed at in review.

## Alternatives

- Classic layered architecture with controllers calling repositories directly. Rejected because the domain would depend on persistence and framework details, and the same workflow would be duplicated for HL7 and REST input.
- Full domain-driven design with aggregates, domain events, and a repository per aggregate. Rejected because the extra ceremony does not serve the learning goal at this scale. init.md asks for rules independent of transport, not a textbook DDD implementation.
- Persistence-ignorant anemic models with all logic in services. Rejected because patient identity and encounter matching rules are real domain behavior and belong with the model and its use case, not scattered across adapters.
