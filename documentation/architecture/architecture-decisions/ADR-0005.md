# ADR-0005: PostgreSQL-backed processing before any message broker

## Status

Accepted, 2026-10-08.

## Context

Healthcare messages arrive twice, arrive out of order, and fail during FHIR persistence. The platform must detect duplicates, retry transient failures, quarantine permanent ones, and recover after a restart. init.md section 6 lists these situations and describes a persistent processing state machine with the states RECEIVED, VALIDATED, PROCESSING, RETRY_PENDING, COMPLETED, and QUARANTINED.

Expected volume is learning-scale: single developer, synthetic data, one workstation. RabbitMQ or Kafka would add a broker service to the local stack, its own configuration, and its own failure modes, and the platform would still need the database row that records what happened to each message. init.md section 6 closes with the instruction to use a PostgreSQL-backed queue first and introduce a broker only after operational behavior is understood.

## Decision

The application PostgreSQL is the durable queue and the state store. The `inbound_messages` table carries `processing_status`, `received_at`, `processed_at`, `error_code`, and `error_summary`, and the `ix_inbound_messages_status_received` index supports polling for due work in receipt order. Duplicate detection uses the `uq_source_message` unique constraint on `(source_system, message_control_id)`.

Retries use bounded attempts with backoff and move through RETRY_PENDING. Permanent validation errors move to QUARANTINED instead of looping. Restart recovery reads persisted state and continues or replays work idempotently. Plan 01 phase 5 creates the table with the state and timestamps this machine needs, and plan 4 implements the transitions.

No message broker runs in the initial implementation. The revision point is explicit: when message rates, retry distributions, and delay requirements are measured, the broker question is revisited with data.

## Consequences

- One less service in the local stack, which keeps the foundation plan's M1 milestone to two databases and the FHIR server.
- Message bookkeeping and state transitions commit together, so there is no gap between "message stored" and "message queued".
- Polling is simple to reason about and to debug, and the status endpoint exposes the same rows an operator would read.
- Throughput is bounded by PostgreSQL and the number of application instances. That ceiling is acceptable now, and it is the signal that would trigger the broker decision later.
- Adding a broker later means extracting the state machine behind a port and keeping the dedup semantics in `source_system` plus `message_control_id`. The domain and ports keep that option open ([ADR-0002](ADR-0002.md)).
- The application owns its scheduling and recovery, so plan 4 carries real implementation work: polling, backoff, attempt limits, and poison message handling.

## Alternatives

- RabbitMQ from the start. Rejected because the operational overhead arrives before any measured need, and init.md section 6 says not to add it during the first implementation phase.
- Kafka from the start. Rejected for the same reason, plus partitioning and consumer group concepts that do not teach healthcare integration at this scale.
- An in-memory queue or `@Async` executor without persistence. Rejected because state is lost on restart, which breaks duplicate detection and the M7 restart and replay demonstration.
- A database table plus an external scheduler for retries. Rejected because it adds another part to operate and the polling loop inside the application is sufficient at this volume.
