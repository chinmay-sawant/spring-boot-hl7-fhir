# ADR-0004: Two-database ownership

## Status

Accepted, 2026-10-08.

## Context

Operational state and clinical state have different owners, access patterns, and lifecycles. Message control ids, processing status, retries, identifier mappings, and audit records belong to the application. Patient, Encounter, and Observation resources belong to the FHIR server.

A single write path spans both stores: an admission updates the application database row and creates FHIR resources. There is no cheap way to make that atomic. init.md section 4 warns that a FHIR transaction provides all-or-nothing behavior inside the FHIR server only, and it does not make the application database and the FHIR database one transaction. init.md section 5 then prescribes two logically separate databases.

## Decision

Two PostgreSQL databases, each with one owner:

- Application PostgreSQL stores `inbound_messages`, `resource_mappings`, and audit metadata. The application owns the schema and applies it with Flyway, in `healthcare-application` only.
- FHIR PostgreSQL stores FHIR resource tables and is written only by the HAPI FHIR server. The application never connects to it, and it is not exposed on a host port in the compose stack.

Each database has exactly one writer. No distributed transaction spans them, and no two-phase commit or XA coordinator is introduced. Cross-database consistency uses idempotent handlers, the `uq_source_message` unique constraint for duplicate detection, and `resource_mappings` plus identifier search for repeatable FHIR writes. The processing state machine reconciles leftovers ([ADR-0005](ADR-0005.md)).

## Consequences

- A failure between a successful FHIR write and the application database update is recoverable. A replay finds the message by control id or finds the FHIR resource by identifier, so work is not repeated.
- No XA infrastructure to operate, and no lock coordination between unrelated databases.
- The two stores are eventually consistent, so message status is the operator's view of outstanding work. `GET /api/v1/messages/{id}` exists for that.
- Accidental cross-database access is hard by construction: there is no route from the application to the FHIR database.
- Schema upgrades are independent. Flyway migrations touch only the application database, and FHIR schema changes come from the server image.
- Verification: plan 01 phase 3 runs the two databases as separate compose services with separate volumes, phase 5 proves `healthcare-fhir` has no Flyway dependency, and phase 6 replays a registration without creating a duplicate Patient.

## Alternatives

- One PostgreSQL instance with two schemas. Rejected because it weakens ownership and makes accidental cross-schema writes easy. The database boundary should be visible, not a naming convention.
- Two-phase commit or XA across both databases. Rejected because the operational cost and coupling are out of proportion to a learning project, and the FHIR server does not expose its transactions for a shared coordinator anyway.
- A saga framework with compensating actions. Rejected at this scale because the PostgreSQL-backed state machine and idempotent replays cover the same ground with far less machinery. That is the plan 4 reliability work, not a distributed transactions framework.
