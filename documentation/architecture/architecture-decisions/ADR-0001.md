# ADR-0001: Modular monolith over microservices

## Status

Accepted, 2026-10-08.

## Context

The platform is a learning project for one developer, and its goal is to understand healthcare interoperability: how HL7 v2 messages represent hospital events, how FHIR resources represent clinical data, and how patient and encounter identity works across both. The architecture brief in init.md section 1 opens with the instruction not to start with microservices and to keep the business logic in a modular monolith connected to a separate FHIR server.

The functional areas interact through shared identity. An admission touches the patient workflow, the encounter workflow, and one FHIR transaction that must contain both resources. A microservice split would put network calls, independent deployments, and eventually distributed transactions between pieces that currently change together, and none of that teaches the healthcare standards the project exists for.

## Decision

The platform is one Spring Boot deployable built from a Maven multi-module project. The modules are `healthcare-domain`, `healthcare-hl7`, `healthcare-fhir`, `healthcare-application`, and `healthcare-integration-tests`. Boundaries are enforced in the build with ArchUnit: the domain depends on nothing outside the JDK, `healthcare-hl7` and `healthcare-fhir` depend on the domain but never on each other, `healthcare-application` may depend on all three, and no package cycles are allowed.

The HAPI FHIR server runs as a separate process because it is an external system the platform integrates with, not a service this codebase owns.

## Consequences

- One deployable and one local stack to run, debug, and reason about. `docker compose up -d --wait` plus one jar covers the whole system.
- Module boundaries are checked by the build instead of by convention, so a bad dependency fails `./mvnw verify`.
- Refactoring across functional areas is a local change, which matters while the domain model is still moving.
- Nothing prevents a class from reaching across module boundaries except the ArchUnit rules, so those tests carry real weight and must stay green.
- Scaling is vertical only. For a single workstation and one developer, that is the right trade.
- If a module ever needs extraction into a service, the ports and the domain isolation make it possible later. The decision is reversible.

## Alternatives

- Microservices from the start. Rejected because it adds operational complexity, network failure modes, and distributed data problems without teaching HL7 or FHIR. init.md section 1 gives the same instruction.
- A single Maven module with no enforced boundaries. Rejected because nothing would stop cycles or framework leakage into the domain, and the boundary discipline is part of what the project teaches.
- Separate deployables per functional area with a shared library. Rejected as a middle ground that keeps most microservice costs while hiding them behind one repository.
